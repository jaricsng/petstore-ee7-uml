### 1.5 Traceability between diagrams

Cross-diagram references are checked by machine, not just by reading. `gen_markdown.py` resolves:

- every `ref` InteractionUse in the interaction overview (15) against the `sd <Name>` frame heading of a diagram;
- every note of the form `ref|see sd|stm|act <Name>` (for example `see stm ShoppingCartBean` in 12b);
- every diagram file named in a legend (for example the traceability legend in 15);
- that every `.puml` has a rendered PNG and SVG.

Any unresolved item fails `render.sh` and `render.sh --check`, and so fails CI. The resolved matrix is published in
[`markdown/README.md`](markdown/README.md#traceability-matrix-cross-diagram-references), and each diagram page lists its
**References** and **Referenced by**. Review result (this revision): 6 of 6 `ref` targets in diagram 15 exist
(three of them, `BrowseCatalogue`, `CreateAccount` and `SignOut`, were missing and have been added as 13e/13f/13g).
In total, 18 references resolve and none are missing.

### 1.6 Frame headings (Annex A)

Annex A defines the heading syntax `[<kind>]<name>[<parameters>]`. The heading "represents the kind, name and
parameters of the namespace enclosing, or the model element owning, the elements shown". It lists eight frame kinds,
seven with an abbreviation:

| Long form | Abbreviation | Used here for |
|---|---|---|
| activity | `act` | Activity diagrams 11a, 11b |
| class | *(none)* | Composite structure diagrams 07a, 07b (the frame **is** the class) |
| component | `cmp` | Component diagram 06 |
| deployment | `dep` | Deployment diagram 08 |
| interaction | `sd` | **All four interaction diagram types**: sequence (13a–13g), communication (14), interaction overview (15), timing (16) |
| package | `pkg` | Class, object, package and profile diagrams whose elements are owned by a package (01–05, 09, 20–28) |
| state machine | `stm` | State machine diagrams 12a–12c |
| use case | `uc` | Use case diagrams 10a, 10b |

**Why `sd` is right for timing, communication and interaction overview diagrams.** `sd` is the abbreviation for an
*interaction* frame, not for "sequence diagram". Clause 17.2.4.1 says the Interaction frame has "'sd' followed by the
Interaction name and parameters", and that the notation inside the frame "comes in several forms: Sequence Diagrams,
Communication Diagrams, Interaction Overview Diagrams, and Timing Diagrams". Clause 17.10.1 adds that interaction overview
diagrams "are framed by the same kind of frame that encloses other forms of Interaction Diagrams", and that the heading
may list the contained lifelines. Diagram 15 now does this with `sd ShoppingJourney lifelines :Customer, …`.

**Corrections made in review.** (1) The class diagrams 01–03 and pattern diagrams 21–28 were headed `class …`. Their
elements are owned by a package, not by a class, so they are now `pkg …` (compare Annex A Figure A.3 ii, where the class
diagram of package P is headed with the package). (2) Several headings contained free text, such as
`act Purchase Pets` or `pkg <<profile>> JavaEE7`. The name part must name the owning element, so they are now
`act PurchasePets`, `pkg JavaEE7`, and so on; the descriptive wording moved to the diagram title. (3) `gen_markdown.py`
now rejects any heading whose kind is not an Annex A kind, whose kind does not match the diagram type, or whose name is
not an element name. The check runs in `render.sh --check` and in CI.

## 2. Conformance notes (PlantUML vs. UML 2.5.1)

PlantUML is used natively with no plug-ins. Where its notation differs from the specification, the
diagram states it explicitly so the models can be used for teaching without misleading students.

| Topic | UML 2.5.1 | Rendering here | Mitigation |
|---|---|---|---|
| Extension (profile) | Solid line, **filled** triangle at the metaclass (clause 12.3.4) | Solid arrow named "extension" (PlantUML has no filled triangle) | Note on diagram 09; hollow triangles there are stereotype Generalizations only |
| Composite structure | Parts inside a classifier frame, ports on border | `rectangle` parts, `portin/portout` | Parts use `name : Type [multiplicity]` syntax |
| Collaboration | Dashed ellipse, internal roles inside ellipse | Dashed ellipse + role bindings, roles listed in a note | CollaborationUse role bindings are dashed lines without arrowheads, labelled at the client end (clause 11.7.4) |
| Communication | Lifelines + numbered messages with arrows on links | Rectangles + links, arrows `→ ←` in labels | Decimal numbering per clause 17.9.1.3 |
| Interaction overview | Activity notation whose nodes are interactions / `ref` | PlantUML activity with `ref sd …` nodes; InteractionUse nodes drawn as rounded actions, not `ref` frames | Heading `sd`, per Figure 17.28 |
| Object diagram kind | Not a separate frame kind in Annex A; InstanceSpecifications are owned by a package | Heading `pkg OrderSnapshot` | Instances named `name : Class` with slot values |
| Extend condition note | Note symbol attached to the «extend» arrow by a dashed line (Fig. 18.3) | `note on link` puts the note beside the arrow, with no anchor line | Note sits directly next to its «extend» label and names the extension point |
| Visibility | `+ - # ~` | Rendered as text (icons disabled) | `skinparam ClassAttributeIconSize 0` |
| Types | UML primitive types | `Float` mapped to `Real`; `List<T>` to `T [*]` | Keeps diagrams language-neutral |
| Decision diamonds | Guards on outgoing edges in `[ ]`; a decision input may be attached as a «decisionInput» note | Question text drawn inside the diamond | All guards are written `[yes]`, `[no]` and so on; the question text is informal |
| Deployment nesting | Nested Nodes | PlantUML collapses a node that has a single child into a dotted name | Diagram 08 uses `set separator none` and an invisible spacer label |
| Timing messages | Message arrow between lifelines | Vertical arrow at the send time | Duration constraints are written in `{ }` (clauses 17.11 and 8.4.4.2) |

## 2a. UML 2.5.1 conformance review (2026-09-30)

Every diagram was reviewed clause by clause against formal/17-12-05. The following changes were made.

| Clause | Rule | Diagrams changed | Change |
|---|---|---|---|
| 17.1, 17.6, 17.9.1.3 | Sequence expressions (message numbers) belong to **communication** diagrams; in a sequence diagram, order is given by vertical position | 13a–13g | `autonumber` removed. Numbering is kept only in communication diagram 14 |
| 17.4.4.1 | Request: `name(args)`. Reply: `[target =] name [(out-args)] [: value]`, dashed line. Create: dashed line, open arrowhead | 13a–13g | Replies rewritten as `operation : value`. Create messages drawn dashed with an open head. Replies routed back through interceptors in the correct order |
| 17.9.1.3 | Sequence term `<integer>[<name>]`: a letter suffix means a **concurrent** thread; alternatives use a guard | 14 | `2.5a/2.5b` became `2.5 [found]` and `2.6 [not found]`; the reply is `2.7: addItemToCart : showcart.faces` |
| 17.11, 8.4.4.2 | Duration constraints are written in braces; no highlight notation exists | 16 | `{0..30 min idle}`, `{d..3*d}`; the highlight was replaced by the `createOrder(..)` message |
| 12.3 | Every applied stereotype must be defined in an applied Profile, or be a standard stereotype or keyword (Table 22.1, Annex C) | 09 and all | Profile 09 rewritten: abstract stereotypes with Extensions, concrete stereotypes by Generalization, tag definitions, and «apply». `gen_markdown.py` now **fails the build** on any undefined `<<stereotype>>` |
| 11.7.4 | CollaborationUse: a dashed ellipse `name : Collaboration`. Role bindings are dashed **lines** labelled at the client end | 07b, 20–29 | `..>` arrows became dashed lines. Pattern role labels such as «creator», «adapter» and «strategy» were **removed** as stereotypes, because roles are expressed only by the bindings. Missing bindings were added |
| 9.8.4 | An InstanceSpecification name is underlined: `name : Class`, or `: Class` when anonymous | 04 | All instance names are underlined |
| 9.5.4 | `/` marks a **derived property**; it is not valid on an Operation | 01, 03 | `/getSubTotal()`, `/getTotal()` and `/fullName()` became `{query}` operations |
| 14.2.4 | A State's internal compartment holds only `entry/exit/do` behaviours and internal transitions | 12a, 12b | Descriptive lines moved to notes. `Shopping` became the submachine state `Shopping : ShoppingCartBean` |
| 14.4.4 | ProtocolStateMachine: `«protocol»` next to the name; state invariants in `[ ]`; transitions `[pre] trigger / [post]` with **no effects**; no entry/exit/do behaviours | 12c | Rewritten as a protocol state machine. JPA callbacks are shown as notes |
| 15.3.4 | A DecisionNode chooses exactly one edge; guards go in `[ ]` | 11a, 11b, 15 | The `split` became a decision/merge, and every guard is bracketed |
| 19.2.4, 19.4.4 | Deployment goes from an artifact to a node (not to another artifact). A deployment spec is attached to the deployed artifact by a dependency. A node is a cube (UML has no database symbol) | 06, 08 | Removed the artifact-to-artifact «deploy». The `persistence.xml` and other specs are `..>` dependencies to the WAR. Database shapes became «executionEnvironment» nodes. Hibernate became an «artifact» «library» |
| 11.2.4, 11.8 | Connectors between parts are solid lines | 07a | The dashed part links became connectors |

**Answer to "does a sequence diagram need sequence numbers?"** No. UML 2.5.1 defines the sequence-expression
prefix (`1`, `2.1`, `2.1a`) only for communication diagrams (clause 17.9.1.3), because a communication diagram has no
time axis. In a sequence diagram the order of OccurrenceSpecifications along each lifeline is shown by vertical
position (clause 17.1: "Along each instance axis the time is running from top to bottom"; clause 17.6 defines the order of fragments by their vertical position), so numbers would duplicate information that the layout
already carries. Many tools (and PlantUML's `autonumber`) offer numbering as a reading aid, but it is **not part of the
UML notation**, and mixing the two styles confuses students. The numbers were therefore removed from 13a–13g. They
remain in communication diagram 14, where they are required.

## 3. Findings raised while reverse-engineering the code

Documenting a system accurately surfaces gaps between intent and implementation. These are shown on the
relevant diagrams as notes, and summarised here for triage. Severity uses a simple High/Medium/Low scale.

| ID | Severity | Finding | Evidence | Diagram(s) | Recommendation |
|---|---|---|---|---|---|
| SEC-01 | **High** | Sign-in never verifies the password; `loginContext.login()` is commented out and `doLogin()` loads the customer by login only | `AccountBean.doLogin()` | 11b, 13b, 02b | Re-enable authentication; migrate to Jakarta Security `IdentityStore` |
| SEC-02 | **High** | `/admin/**` pages and `/rest/**` resources have no authentication or role check; `UserRole.ADMIN` is unused | `web.xml` (no security-constraint), endpoints | 10, 13c | Add `security-constraint`/`@RolesAllowed`, OAuth2/OIDC for REST |
| SEC-03 | High | Passwords hashed with unsalted single-round SHA-256 | `Customer.digestPassword()` | 01, 28 | PBKDF2/bcrypt/Argon2 with per-user salt (OWASP ASVS V2.4) |
| SEC-04 | Medium | `CustomerEndpoint` serialises `Customer.password` (hash) in JSON/XML | `@XmlRootElement` without `@XmlTransient` | 13c | Use DTOs or `@XmlTransient`/`@JsonbTransient` |
| SEC-05 | Medium | Credit-card number stored in clear text | `CreditCard` `@Embeddable` | 01, 28 | Tokenise via payment provider; never persist PAN (PCI DSS 3.4) |
| SEC-06 | Medium | `debug.xhtml` exposes thread stack, working directory and memory unauthenticated | `DebugBean` | 10 | Remove from production build or restrict by role |

## 4. Keeping diagrams and code in sync

1. **Docs-as-code.** `.puml` sources live beside the code and change in the same PR as the Java they describe.
2. **CI gate.** [`.github/workflows/docs.yml`](../../.github/workflows/docs.yml) runs `render.sh --check` on every PR and fails on PlantUML syntax errors, missing renders, stale generated pages, broken links or an invalid OpenAPI contract. It uploads the rendered diagrams as a build artifact for review.
3. **Markdown pages are generated, never hand-edited.** `gen_markdown.py` reads the `' @kind:` / `' @summary:` header in each `.puml` and embeds the PNG plus the verbatim source; `--check` detects drift.
4. **Stereotype lint.** `gen_markdown.py --check` rejects any `<<name>>` that is neither a UML 2.5.1 keyword or standard stereotype nor defined in profile 09.
5. **Pre-commit hook.** The `docs-check` hook in [`.pre-commit-config.yaml`](../../.pre-commit-config.yaml) runs `./docs/render.sh --check` when files under `docs/` are staged.
6. **Pull-request template.** [`.github/pull_request_template.md`](../../.github/pull_request_template.md) includes the item *"UML, architecture and API docs updated for changed classes, flows or endpoints"*.
7. **Traceability.** File names are numbered by diagram kind; each diagram names the Java classes it depicts. Consider an ArchUnit test that asserts the package dependencies in diagram 05.
8. **Optional generation.** For the class diagrams, tools such as `plantuml-generator-maven-plugin` can emit a baseline from bytecode for diff-review against the curated diagrams here.
